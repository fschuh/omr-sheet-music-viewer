# Printed-fingering recognition: measured pilot and recommendation

2026-09-19, Task 13. **Do not adopt automatically; do not train a new model yet.**
The bounded pilot is complete. The broader planned recognition acceptance set is
not: real scans, different fingering fonts/editions, measure-number negatives and
held-out recognition pages still need annotation and evaluation. This is research,
not a newly enabled application feature. Tasks 01–12 remain the usable default-off
overlay experiment, with their separate platform/device acceptance limitations.

## Data and protocol

[The annotation manifest](fingering-recognition-pilot.json) pins PDF, raster and
authoritative recognition packet hashes. [Raw results](fingering-recognition-results.json)
include every candidate, confidence, box, gold note ID, model hash and stage count.
No original PDF, recognition cache, production annotation, or model was modified.

Eight manually selected, completely annotated windows cover:

- Chopin 25/9, page 1: four two-digit chord stacks and three sparse upper-note
  fingerings (11 digits), plus time signature, title/page numbers and articulation
  negatives.
- Chopin 25/2, page 1: four single-note fingerings and a negative window containing
  six triplet 3s, italic text, slurs and noteheads.
- Chopin 25/6, page 1: an octave-indication negative. This page has no accepted OMR
  association; it contributes **only** a negative image crop. Its existing physical
  staff validation failure remains untouched.

All digits 1–5 occur, but the positive distribution is very small and unbalanced:
six 1s, two 2s, one 3, three 4s and three 5s.

Coordinates use a 1300-pixel page width; inference uses native-resolution crops.
Every glyph crop, marked context and negative window was visually checked before
the final run. Chord gold IDs follow the visible top-to-bottom correspondence;
they are not generated by the association heuristic being evaluated. Gold IDs are
bound to the exact packet hash so regeneration cannot silently redefine the labels.
Only the first physical upper staff is considered in the association experiment.

These are **development crops from one clean digital edition**, not a random,
whole-page, held-out or multi-font benchmark. Cropping supplies favorable search
regions. Reported precision applies only to these fully annotated windows; no
unannotated page areas are counted as either success or failure. Digit/negative
window selection was manual; no thresholds were optimized on a held-out set.

## Existing-tool measurements

RapidOCR 3.7.0 uses its already installed PP-OCRv4 detector/recognizer ONNX models,
CPU, one intra/inter-op thread, orientation classification off, score threshold
0.5. This is an **output constraint** (`^[1-5]$`), not a retrained or lexicon-constrained
decoder. Multi-character strings are rejected, not split into convenient digits.
The oracle transcription test bypasses detection on gold glyph crops. RapidOCR
supports separate detection/recognition controls; the script explicitly resets
these because call flags persist in this installed version. See the
[versioned parameter documentation](https://rapidai.github.io/RapidOCRDocs/v3.7.0/install_usage/rapidocr/parameters/).

Location scoring uses deterministic one-to-one matching with box IoU ≥0.1. This
lenient threshold measures a candidate near the glyph, **not** accurate masking or
erasure bounds. A box covering a stack cannot recover both digits. Value scoring
additionally requires the correct digit; assignment scoring additionally requires
the exact gold note ID. Incorrect/extra candidates stay in precision denominators.
Undefined precision (no predictions) is null, never 100%.

| Stage | Correct / proposed | Recall against 15 gold digits | Precision |
| --- | ---: | ---: | ---: |
| OCR text proposals, location only | 15 / 34 | 100% | 44.12% |
| OCR single-digit candidates, location | 15 / 21 | 100% | 71.43% |
| OCR candidates, correct transcription | 15 / 21 | 100% | 71.43% |
| OCR + nearest-note baseline, correct value **and** note | 11 / 21 | 73.33% | 52.38% |
| PDF ASCII digit candidates, location/value | 0 / 8 | 0% | 0% |
| OCR transcription with oracle glyph crops | 15 / 15 | 100% | 100% |
| Association with oracle boxes/values, nearest note | 11 / 15 | 73.33% | 73.33% |
| Association with oracle boxes/values, ambiguous columns rejected | 4 / 4 | 26.67% | 100% |

The last two rows deliberately remove recognition errors to isolate association.
The research-only baseline looks below a digit, within six horizontal pixels and
70 vertical pixels in the normalized coordinates, then chooses the nearest note.
It misassigns **all four lower stack digits to the upper note**. Rejecting every
multi-note column avoids these errors but leaves only four single-note assignments.
Neither heuristic is installed in the viewer or used to repair authoritative links.
Full-pipeline precision divides correct value-and-note results by all 21 digit
candidates, including candidates with no assigned note; it is not conditional
precision after discarding abstentions.

Hard-negative review: every triplet 3 was accepted as a fingering candidate, with
confidence 0.99812–0.99990. The scores overlap and exceed those of some true
fingerings, so a higher generic OCR confidence threshold does not solve semantic
classification. The title's `25`, page `42`, octave `8`, unrelated text and
articulation were rejected by the single-digit filter. The time-signature crop
was read as a non-digit. This is not evidence those negative categories are safe
across other fonts/layouts. Measure numbers remain an explicit dataset gap.

Poppler text extraction produced no ASCII finger candidates in the two positive
windows. Visible finger glyphs were encoded as control characters; the eight
ASCII candidates instead came from six triplets and the 2/4 signature. PDF positions
can be useful proposals in other PDFs, but neither a glyph-code substitution table
learned from this edition nor ASCII filtering is a general recognition solution.
The script preserves those control characters for counting and does not reinterpret
them as digits. Original PDFs are read only.

The existing HOMR-generated, unmodified source MusicXML contains zero `fingering`
elements on both positive pages. Source inspection also finds no piano-fingering
recognizer in this branch; title OCR does not provide this capability. Thus the
current OMR output recovers 0/15 annotated fingerings, with no positive predictions
and undefined precision. This does **not** assert a failure rate for an unimplemented
HOMR fingering classifier.

Audiveris is not installed locally, so it was **not benchmarked**. Its
[handbook](https://audiveris.github.io/audiveris/_pages/guides/specific/fingering_plucking/)
describes guitar-oriented 0–4 fingering, explicit detection switches and MusicXML
export. The current [Shape.java source](https://raw.githubusercontent.com/Audiveris/audiveris/master/app/src/main/java/org/audiveris/omr/glyph/Shape.java)
does include `DIGIT_5` alongside 0–4. Therefore neither “no piano 5 support” nor
“reliable piano recognition” follows from the documentation alone. A version-pinned
Audiveris benchmark with fingering detection enabled is a remaining comparison;
no performance is attributed to it here. Tesseract is also not installed/tested.

## Proposed confirmation workflow — not implemented in this research task

1. Keep detected candidates separate from effective fingerings. Store PDF hash,
   page/raster and annotation revision, original source box/crop, raw transcription,
   OCR confidence and association evidence. Confidence is not a correctness promise.
2. Show the crop beside the highlighted proposed note or chord, its current
   effective value/provenance, and explicit **Confirm**, **Choose another note**,
   **Edit digit**, and **Reject** actions. Ambiguous stacks require individual
   note confirmation; do not silently choose by proximity or pitch.
3. On confirmation, create a revision-bound adopted-source value, preserving the
   raw reading. Apply the shared resolver: an explicit user override still wins.
   Replacing a user override requires a separate explicit action with undo.
4. Offer exclusion of the printed passage independently, previewing affected
   anchors. Adoption does not remove the old printed mark or guarantee room for a
   new label. Do not automatically hide unrelated notes in an adopted stack.
5. Changed geometry/identity invalidates pending proposals and adopted associations
   for review. Never remap them silently. Keep original crops/provenance recoverable.

No printed-digit erasure, white masking, background reconstruction, PDF rewriting,
automatic source adoption or custom model training is justified by this pilot.
The immediate bottlenecks are semantic negatives and chord association, not the
ability to transcribe these 15 clean glyphs. Gather a separate, balanced, held-out
set with different editions/fonts, real skew/noise, substitutions and alternatives,
left-hand/below-staff marks, multiple voices, measure/tuplet/octave negatives, and
manually verified per-digit note IDs before estimating recognition implementation
or a training project. Revisit model training only after that existing-tool
comparison establishes a repeatable benefit worth the data/maintenance burden.

## Reproduce and verify

Use the Task 07 prepared fixtures and locally cached RapidOCR models. No network,
model download, GUI, or application-profile access is needed. Missing models or
changed fixture identities fail before inference. The two paths below write only
derived research outputs; source PDFs remain unchanged.

```sh
.venv/bin/python tools/fingering-recognition-pilot.py --prepare-only
.venv/bin/python tools/fingering-recognition-pilot.py --output /tmp/fingering-recognition-repeat.json
.venv/bin/python -m unittest discover -s tools -p 'test_fingering_recognition_pilot.py' -v
```

Use `--pdf-root /path/to/Classical` if needed. Review generated contexts and glyph
atlas under ignored `testdata/fingering-recognition/`. Results are deterministic
apart from elapsed seconds; model/manifest/input hashes are recorded. Scoring tests
cover merged and duplicate boxes, negatives, wrong values versus wrong notes,
abstentions, control-character extraction, coordinate scaling, and rescoring the
committed result artifact. Runtime dependency warnings are recorded separately
from recognition failures; no dependency versions were changed for this task.

Final verification: nine scoring tests passed; a second complete OCR run exactly
matched the committed artifact after excluding elapsed seconds. Full web tests and
production build passed, as did 27 worker tests, 135 HOMR geometry/sidecar tests
(plus six subtests), six native tests and verification of all 16 matched fixtures.
Existing build chunk-size and Python dependency/deprecation warnings remain.
No additional browser/device coverage is claimed by this research-only change.
